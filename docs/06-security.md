# 06 · 安全分析与风险清单

> 本文基于对 `server.py`（1707 行）、`docker-entrypoint.sh`、`docker-compose.yml`、CI 流水线的静态审计，以及一台生产实例的运行观测。结论区分**已验证事实**与**推断**，风险等级按 CVSS 思路定性给出。

## 1. 威胁模型

| 攻击者位置 | 能做什么 | 最关心什么 |
| --- | --- | --- |
| 网络中间人 | 截获 HTTP 明文流量 | 管理员口令、会话 token、卡密明文 |
| 未授权外部请求者 | 直接调用 `/api/verify_card.php`、爆破 `/api/login` | 猜中有效卡密、爆破管理员口令 |
| 数据库文件窃取者 | 拿到 `cards.sqlite3`（如备份泄露、卷权限错误） | 还原卡密明文、拿到口令哈希 |
| 有管理员权限的内部人 | 全部管理接口 | 导出卡密、重置数据 |
| 上游供应链 | 控制 GitHub 仓库或 token | 通过一键更新投放任意代码 |

## 2. 已实现的安全措施（值得肯定）

| # | 措施 | 位置 | 评价 |
| --- | --- | --- | --- |
| 1 | 口令用 **scrypt**（N=2^14, r=8, p=1）+ 16 字节盐 | `hash_password()` | 参数合理，单次约 50–100 ms，离线爆破成本高 |
| 2 | 口令比对用 **`hmac.compare_digest`** 常数时间 | `check_password()` | 消除时序侧信道 |
| 3 | 卡号 **80 bit 随机熵**，不可预测 | `make_card()` | 暴力枚举不可行 |
| 4 | 库内**不存卡号明文**，只存 HMAC 摘要 + 加密密文 | `digest()` / `seal_code()` | 单库泄露 ≠ 卡号泄露 |
| 5 | 加密密钥派生做**领域分离**（`b"card-secret-v1"` 标签） | `seal_code()` | 避免同一密钥跨用途复用 |
| 6 | 每次加密用**随机 12 字节 nonce** | `seal_code()` | 相同卡号密文不同，防模式分析 |
| 7 | 静态文件**目录穿越防护**：`resolve()` + `relative_to()` | `serve_static()` | 正确的写法，比字符串前缀匹配可靠 |
| 8 | 备份文件名**白名单**：只允许备份目录内 `.sqlite3` | `backup_path()` / `delete_backup()` | 拒绝 `../`、反斜杠、绝对路径 |
| 9 | 请求体 **1 MB 上限** | `read_params()` | 防内存耗尽 |
| 10 | JSON 响应统一 `no-store` + `nosniff` | `send_json()` | 防缓存泄露与 MIME 嗅探 |
| 11 | 容器**根文件系统只读**、`no-new-privileges`、非 root（UID 10001） | compose / Dockerfile | 显著缩小落点后的破坏面 |
| 12 | 启动时**拒绝弱默认值**（`LICENSE_BLOB` / 短口令） | `docker-entrypoint.sh` | 默认安全，必须显式配置才能跑 |
| 13 | CI **反向测试**"不安全配置必须起不来" | `build-image.yml` smoke | 把安全假设变成可回归的测试 |
| 14 | 备份用 **SQLite 在线备份 API** | `snapshot_database()` | 避免静默损坏的快照 |
| 15 | 更新包解压前校验路径/链接/数量/体积，静态目录**先临时后替换、失败回滚** | `install_tree()` | 防目录穿越与半更新状态 |
| 16 | 全部 SQL 使用 **`?` 参数化** | 全文 | 无字符串拼接注入点 |
| 17 | 删除卡密时输出**审计行** | `do_POST` | 唯一的审计痕迹 |
| 18 | 管理员越权拦截统一走 `require_user(admin_only=True)` | HTTP 层 | 权限判定集中，不易遗漏 |

## 3. 风险清单

### 3.1 高危

#### R1 · 生产实例以明文 HTTP 暴露

**事实**：生产容器直接映射 `0.0.0.0:48192->8080`，未观察到前置 TLS 反向代理。`/health` 可直接从该端口访问，说明 HTTP 服务对外开放。

**影响**：管理员登录口令、Bearer token、客户端卡密全部明文过网，任何中间人可完整窃取。拿到 token 后 12 小时内可完全接管后台（生成/删除卡密、下载数据库备份、触发更新）。

**修复**：
1. 端口改为只绑本机：`127.0.0.1:48192:8080`；
2. 前置 Caddy/Nginx 做 TLS（仓库已带 `deploy/Caddyfile`，只需配 `CARD_DOMAIN`）；
3. 防火墙仅放行 80/443，关闭 48192 公网入口。

#### R2 · 登录接口无失败限流与账户锁定

**事实**：`/api/login` 对任意来源无限次尝试，仅靠 scrypt 的计算成本限速。

**影响**：scrypt（约 80 ms/次）把单 IP 爆破压到约 12 次/秒。若口令为弱口令（如姓名+年份），分布式爆破仍可在可接受时间内成功。账户模型只有 4 个管理员、无普通用户（实测），爆破面小但价值极高。

**修复**：加"同 IP / 同用户名连续失败 5 次锁定 5 分钟"的内存计数；失败响应增加随机延迟；管理员口令强制 ≥ 16 位。

#### R3 · 在线更新构成完整供应链攻击面

**事实**：`download` 模式从 `CARD_UPDATE_REPO`（默认 `heijiji0527/card-service`）拉取 `master` 分支源码包，解压后直接由容器执行，**无签名校验、无哈希固定**。

**影响**：
- 上游仓库被入侵 / 分支被强推 → 服务器执行任意代码；
- `CARD_UPDATE_REPO` 环境变量可被改指向攻击者仓库；
- 若配置了 `GITHUB_TOKEN`，其权限范围也需评估（应为只读）。

**缓解现状**：只用 `master` 最新提交、留存源码包可回看、Git 模式下只允许快进。
**修复**：固定到具体 commit/tag 而非分支；对源码包做 SHA256 白名单校验；更新前强制自动备份；`GITHUB_TOKEN` 使用仅 `public_repo` 只读最小权限。

### 3.2 中危

#### R4 · 异常原文直接回传客户端

```python
except Exception as exc:
    self.send_json(500, response("error", str(exc)))
```

**影响**：SQLite 错误、文件路径、内部函数信息可能泄露，为后续攻击提供地图（如暴露 `/data/cards.sqlite3` 真实路径）。

**修复**：对外返回通用文案 + 错误 ID，详情只写服务端日志。

#### R5 · 普通用户可见全部卡密元数据

**事实**：`GET /api/cards` 对任何已登录用户返回**全量**卡密（98 条无分页），普通用户只是 `card_code` 为 `null`，仍能看到 `device_uuid`、`app_id`、`note`、到期时间。

**影响**：设备 UUID 属个人信息；运营备注可能含渠道/客户信息。普通用户无业务必要看全量列表。

**修复**：普通用户只返回聚合统计；或引入"按归属"过滤。

#### R6 · 无卡密解绑能力，只有删除重建

**事实**：`device_uuid` 一旦绑定无接口可清空，管理员只能删卡重发。

**影响**：用户换机 = 卡密作废，运营成本与投诉上升。这是**产品缺口**而非漏洞，但会诱导管理员滥用删除权限（删除会丢失 `activated_at` 历史）。

**修复**：增加 `POST /api/cards/unbind`，清空 `device_uuid`/`app_id` 并按需重置 `expire_time`，同时写入审计。

#### R7 · 会话模型：内存态、无撤销列表、无并发限制

**事实**：`SESSIONS` 为进程内字典，TTL 12 小时滑动续期；不记录 UA/IP；登出仅删当前 token。

**影响**：服务重启导致所有人掉线（可用性问题）；无法"踢出某用户所有会话"；token 泄露后除等 12 小时无强制失效手段。

**修复**：会话落库（可加 `sessions` 表）；提供"强制下线"；绑定 UA 指纹。

#### R8 · 加密缺完整性保护

**事实**：`seal_code` 是纯流加密（HMAC-CTR），**无 MAC/AEAD**。

**影响**：能写数据库者可做比特翻转，使管理员看到错误卡号。实际风险低（写库权限已高于此），但不符合现代密码学实践。

**修复**：改用 AES-GCM；或 HMAC-then-Encrypt 增加 16 字节 tag。

### 3.3 低危 / 设计取舍

| # | 问题 | 说明 | 建议 |
| --- | --- | --- | --- |
| R9 | 卡号校验位未被验证 | `make_card()` 生成的末 4 位 HMAC 校验段，`verify_card()` 未单独校验，仅作为整体参与 HMAC | 查表前先校验格式，可提前拦截无效请求、降低无效查询 |
| R10 | 无审计日志 | 仅删除卡密时 `print` 一行；生成、启停、恢复、更新均无记录 | 增加追加式审计表（操作人/动作/对象/时间） |
| R11 | 无速率限制的公开验证接口 | `/api/verify_card.php` 无频率控制 | 加 IP 维度令牌桶，防被当作探测/DoS 入口 |
| R12 | `/api/restart` 可被管理员反复触发 | 无冷却时间 | 加最小间隔（如 60 秒） |
| R13 | 时间依赖系统时钟 | 到期判断用 `datetime.now(utc)`，NTP 大跳变会影响判定 | 关键主机启用 NTP 并监控偏移 |
| R14 | 口令下限仅 8 位 | `users/create` 校验 8–256 | 提到 12 位并加复杂度提示 |
| R15 | SQLite 未启用 WAL | 未观察到 `PRAGMA journal_mode=WAL`，并发写靠 `timeout=15` 重试 | 初始化时启用 WAL，改善并发与崩溃恢复 |
| R16 | 无 CSP 响应头 | 仅 `nosniff`，无 `Content-Security-Policy` | 反向代理层加 CSP（Caddyfile 已有 HSTS/XCTO） |
| R17 | 备份下载即时生成 | 每次请求都做一次完整快照 | 高频调用会放大 IO，建议复用最近快照 |

## 4. 关键运维约束（必须记住的一条）

> **`CARD_SECRET` 一旦投产就不可更换。**
>
> 它同时是 `card_hash` 的计算密钥。更换后所有既有卡密的哈希失配，客户端一律收到"卡密不存在"，且旧密文也无法解密 —— 数据等价于永久作废。
>
> 因此：备份数据库时**必须同时**离线保管 `CARD_SECRET`；迁移服务器时两者一起搬；任何"定期轮换密钥"的安全策略在此项目上都不适用，除非接受全量重发卡密。

## 5. 加固优先级建议

| 优先级 | 动作 | 预计影响面 |
| --- | --- | --- |
| **P0** | 关掉 48192 公网入口，前置 TLS 反代 | 消除流量窃听 |
| **P0** | 登录失败限流 + 管理员口令 ≥16 位 | 消除在线爆破 |
| **P1** | 500 错误通用化，详情只进日志 | 消除信息泄露 |
| **P1** | 更新固定 commit + 哈希校验 + 更新前强制备份 | 收敛供应链风险 |
| **P2** | 普通用户卡密列表做最小化 | 降低数据暴露 |
| **P2** | 增加解绑接口 + 审计表 | 提升可运营性 |
| **P3** | 会话落库、WAL、AES-GCM、CSP | 体系化加固 |

## 6. 审计方法与局限

**已做**：全量阅读 `server.py` 关键路径（配置、认证、验证、备份、更新、HTTP 层）、部署与 CI 配置、生产容器状态与健康检查、数据库结构统计。

**未做**（因此结论有边界）：
- 未做动态渗透测试（无授权范围外的探测行为）；
- 未对前端 JS 产物做反混淆级的逐行审计（`static/assets/*.js` 为 Vite 构建产物，逻辑以 `frontend/src` 源码为准）；
- 未验证反代层实际配置（生产未见独立反代进程处理该端口）；
- 未做依赖 CVE 扫描（Python 侧零第三方依赖，风险面极小；前端依赖见 `package-lock.json`）。
