# 01 · 项目概览

> 版本基线：**v1.2.0**（`CHANGELOG.md` 记录日期 2026-10-25）
> 更新源（`CARD_UPDATE_REPO`）：`quanquna0319/card-service` · 分支 `main`
> 原始来源：`heijiji0527/card-service`（本仓库为其后续维护版本）

## 1. 这是什么

`card-service` 是一个**自持的卡密（License Key）验证服务 + 浏览器管理后台**。它由两个部分构成：

| 组成 | 实现 | 作用 |
| --- | --- | --- |
| 被验证方（客户端） | 既有样本客户端 | 向 `/api/verify_card.php` 提交 `card_code` + `app_id` + `uuid` |
| 验证服务端 | `server.py`（Python 标准库，1707 行） | 校验卡密、激活计时、设备绑定、下发到期时间 |
| 管理后台 | React 19 + HeroUI 3 + Tailwind 4 构建到 `static/` | 生成/编辑/禁用卡密、管理账户、备份、在线更新 |

设计上的关键取舍：**不替换客户端协议**。服务端刻意保留 `verify_card.php` 这个 PHP 风格的接口名与表单编码格式，使既有客户端无需任何改动即可指向新服务器。

## 2. 解决的实际问题

传统卡密方案通常依赖第三方授权平台（远程 SaaS），存在三个痛点：

1. **可控性差** —— 卡密有效期、封禁、解绑都要走平台后台，无法自建。
2. **协议锁定** —— 客户端已内置的验证请求格式改不动。
3. **数据不在自己手里** —— 用户与授权数据存储在第三方。

本项目把这三件事收回到单机：一个 SQLite 文件 + 一个 Python 进程即可完整承载，数据完全自持。

## 3. 角色模型

系统只有两种角色，边界清晰（`users.role` 字段约束为 `admin` / `user`）：

| 能力 | 普通用户 | 管理员 |
| --- | --- | --- |
| 登录、查看概览 | ✅ | ✅ |
| 查看卡密列表 | ✅（不含明文） | ✅（含明文，可复制） |
| 生成 / 编辑 / 启用停用 / 删除卡密 | ❌ | ✅ |
| 查看用户列表、创建账户、停用账户 | ❌ | ✅ |
| 备份下载 / 恢复 / 删除、重启服务、在线更新 | ❌ | ✅ |

实现上通过 `require_user(admin_only=True)` 统一拦截，越权返回 **403**，未登录返回 **401**。

> ⚠️ 注意一个设计事实：卡密**明文**只在管理员请求时下发。普通用户拿到的列表经过了 `open_code()` 过滤，无法看到明文。旧版本数据库里的历史卡密只存过 HMAC 摘要，无法还原，必须重新生成。

## 4. 授权生命周期（本项目的核心语义）

这是理解整个系统最关键的部分。卡密有三种状态与两种"起算方式"：

```
                    ┌──────────── 首次成功验证 ────────────┐
   [unused] ────────┤                                      ├──> [active] ──> 到期 ──> 验证失败(已过期)
       │            └──────────────────────────────────────┘         │
       │                                                             └──> 管理员停用 ──> [disabled]
       └── 管理员停用 ──> [disabled] ── 管理员启用 ──> [unused] 或 [active]
```

**两种到期语义**（`verify_card()` 中的分支）：

- **相对周期**：生成时 `expire_time` 留空 → `unused`。首次成功验证时以 `当前时间 + 周期` 计算到期，写入 `expire_time` 并同时写 `activated_at`。**未激活不计时**，卡密可以长期囤放。
- **固定到期**：生成时指定 `expire_time`（必须是未来时间）→ 到点即失效，与何时首次验证无关。

**设备绑定**：首次成功验证会写入 `device_uuid` + `app_id`。之后若 `device_uuid` 或 `app_id` 任一不一致，直接拒绝（"卡密已绑定其他设备"）。这是**一卡一机**策略，没有解绑接口 —— 换设备只能由管理员删除重建。

周期常量（`DURATIONS`）：

| card_type | 时长 |
| --- | --- |
| `month` | 30 天 |
| `half_year` | 180 天 |
| `year` | 365 天 |

> 注意这是**固定天数**而非自然月/自然年，所以"月卡"在 2 月激活时会跨到 3 月同一天+，不存在按日历月末对齐的逻辑。

## 5. 功能全景

**卡密管理**
- 单张或批量生成（1–1000 张，`MAX_CARD_COUNT`）
- 三种周期 + 可选固定到期时间
- 备注（≤ 80 字符）、启用/停用、批量删除
- 管理员可见完整明文，支持单张复制、复制全部

**账户管理**
- 创建 `user` / `admin`（用户名 3–32 位，密码 8–256 位）
- 停用/启用账户（禁止停用自己）

**运维能力**
- 一键备份 + 下载、历史备份列表、上传恢复、删除单份或清空
- 网页内重启服务（以退出码 0 退出，靠进程管理器拉起）
- 在线更新：Git 拉取 / 下载源码包 / 自定义命令三种策略

**客户端验证**
- `POST /api/verify_card.php`，表单编码，兼容既有客户端

## 6. 技术栈速览

| 层 | 选型 | 说明 |
| --- | --- | --- |
| HTTP 服务 | `ThreadingHTTPServer` + `BaseHTTPRequestHandler` | 零第三方依赖，无 Flask/FastAPI |
| 存储 | SQLite（标准库 `sqlite3`） | 单文件，`CARD_DB` 可指定路径 |
| 密码哈希 | `scrypt`（N=2^14, r=8, p=1）+ 16 字节随机盐 | 格式 `scrypt$<salt>$<digest>` |
| 卡密摘要 | HMAC-SHA256(`CARD_SECRET`) | 用于查表与防篡改 |
| 卡密明文存储 | HMAC-SHA256 派生密钥流的流加密（CTR 形态） | 数据库单独泄露不等于卡号泄露 |
| 会话 | 进程内内存字典，TTL 12 小时 | 重启即失效，需重新登录 |
| 前端 | React 19 / HeroUI 3.2 / Tailwind 4 / Vite 5 / TS | 构建产物落到 `static/` |
| 打包 | Docker 多阶段 + GHCR | 多架构 `linux/amd64` + `linux/arm64` |
| CI | GitHub Actions | 构建推送 + 冒烟测试（拒绝弱默认值） |
